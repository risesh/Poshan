# Poषण — website

Poषण ("foods that heal") is an ecommerce brand for healthy foods rooted in Ayurvedic
tradition. This repo is its website.

## Design system — always use it, never improvise

The brand's colors, type scale, spacing, and component patterns are documented in
[`Design.md`](Design.md) at repo root. That document is the source of truth for what the
brand looks like.

The enforcement mechanism is [`assets/css/tokens.css`](assets/css/tokens.css) — a CSS
custom-property file mirroring `Design.md`'s `:root` block exactly.

**Rules for any new page or component:**
- Import `assets/css/styles.css` (which itself imports `tokens.css`) — don't write a new
  standalone stylesheet.
- Never hardcode a brand hex, font-family, or radius. Use the `var(--*)` tokens
  (`--color-ink`, `--color-teal`, `--color-bone`, `--font-display`, `--font-editorial`,
  `--font-mono`, `--radius-card`, etc.) — see `tokens.css` for the full list.
- Before building a new UI pattern, check whether `styles.css` already has one (nav, hero
  split, product card, pill/attribute tag, philosophy banner). Reuse the existing class
  before inventing a new one.
- If `Design.md` changes (new color, new type rule), update `tokens.css` to match in the
  same change — they must never drift apart.

## Design reference — the exact source, not a vibe

`design/Poshan Homepage (standalone).html` is the raw export from Claude Design
(claude.ai/design), handed over specifically so this site matches it exactly. It was
built carefully to spec — treat every pixel/color/copy value in it as intentional, not
negotiable.

**It is not readable as-is.** It's a self-executing JS bundle (a `.dc.html` "standalone"
export), not plain HTML — the real markup lives inside a `<script type="__bundler/
template">` tag as a JSON-escaped string. Reading the raw file directly, or worse,
half-remembering it from earlier in a conversation, is exactly how mistakes happen (see
incident below). Use the decoded, greppable copy instead:

- `design/decoded-source.html` — plain HTML/inline-styles, regenerated by
  `python3 design/decode.py` whenever the standalone export is replaced with a newer one.
  This is committed, so it's always available without re-running the decoder.
- It's a full-funnel design canvas — homepage (`t1`/`1a`), login/signup (`t2`), product
  detail/cart/our story (`t3`), checkout (`t4`), order confirmation (`t5`). Built so far:
  homepage (`1a` → `index.html`), Our story (`3c` → `our-story.html`), product detail
  (`3a` → `kefir.html` — only product the source fully specifies; the other three product
  pages reuse its template with placeholder ingredient/nutrition content, see below).
  Cart page, login/signup, checkout, and order confirmation are still reference-only.

**Placeholder content — product pages other than Kefir.** The design source only mocked
up one product detail page (Kefir, `3a`). `punjabi-mango-pickle.html`,
`lacto-fermented-carrots.html`, and `dryfruit-millet-laddoo.html` reuse that template but
their description/ingredients/nutrition-facts content is authored for the prototype (in
Poshan's `Design.md` voice), not sourced or verified — each has an HTML comment saying so
near the top. Don't treat their kcal/ingredient values as real; replace before launch.

**Hard rule for any layout/visual value** (padding, margin, width, font-size, color,
copy text — anything that could be "close enough" but wrong): grep it out of
`design/decoded-source.html` first. Do not estimate a percentage from a fixed-pixel
value, do not eyeball proportions from a screenshot, do not rely on memory of having
read it earlier in the session. If the exact value isn't in the decoded source for the
thing being built, say so explicitly instead of inventing a plausible-looking number.

**Incident that motivated this rule:** the homepage hero's left inset was ported as
`padding-left: 8%` (an estimate) instead of the source's actual `padding-left: 200px`
(a fixed value, `grep -n 'padding: 80px' design/decoded-source.html`) — and a second
attempt "fixed" it by matching the nav's `56px` gutter, also never checked against the
source. Both were guesses that looked reasonable and were wrong. Grepping the exact
value the first time would have prevented both.

**Verify, don't just eyeball, after building:** for a section built from the decoded
source, spot-check computed layout against literal source values — e.g. via a headless
browser (`el.getBoundingClientRect()`) compared against the grepped px numbers — the way
a unit test would, rather than declaring it done from a screenshot alone.

## Generated data files — same pattern as decode.py

`Quotes.txt` (repo root) is the human-editable source for the rotating footer quote.
`build-quotes.py` parses it into `assets/js/quotes-data.js` (a committed
`window.POSHAN_QUOTES` array — plain `<script>` tag, no fetch/build step, so it works
under `file://` too). Re-run `python3 build-quotes.py` after editing `Quotes.txt`; don't
hand-edit `quotes-data.js`. Any page that includes the `.philosophy` footer banner should
load `quotes-data.js` before `main.js` and mark its `<blockquote>` with
`data-random-quote` — the quote re-rolls on every load of that page, not just the
homepage. Keep the element's static fallback text as the exact source-authored quote (the
Leigh Hunt one), since that's what renders if JS is unavailable.

## Cart

`main.js` keeps cart state as `{ productId: qty }` in `localStorage` (key `poshan:cart`),
shared across pages via `[data-cart-link]` nav elements. Product cards opt in with
`data-product-id="<slug>"` on the `.card` element. Clicking `.card__add` swaps it for a
`.card__qty` "− N +" stepper (hidden by default — note `.card__qty[hidden]` has to
explicitly re-assert `display:none`, since author-origin `display:flex` on `.card__qty`
otherwise beats the UA's `[hidden]` styling regardless of specificity); decrementing to 0
swaps back to the Add button. The stepper's visual style (border/radius/DM Mono
"−"/"+") is lifted from the product-detail and cart screens in the design reference
(`design/decoded-source.html`, search `qty` / `−`) — the homepage card itself was never
mocked up with one, so match those screens' style rather than inventing a new one.
Out-of-stock buttons use the native `disabled` attribute (no `data-product-id`, no
stepper markup at all), not a JS-level guard.

**`VALID_PRODUCT_IDS` in `main.js` must be updated whenever a `data-product-id` is added,
removed, or renamed anywhere in the site.** `getCart()` prunes any stored cart entry
whose id isn't in that set. This exists because it already broke once: renaming Kefir's
id from `kefir` to `kefir-500ml` left old carts with an orphaned `{"kefir": N}` entry —
invisible on every page (nothing has that id anymore) but still counted in the nav's
total, so the total silently diverged from what was visibly in any product card. Forgetting
to update the whitelist after a future rename would reintroduce exactly this bug, just
silently instead of loudly.

**Cross-tab/window sync:** `main.js` listens for the `storage` event (fires in other
tabs/windows on the same origin when `localStorage` changes) and `pageshow` with
`event.persisted` (fires when a tab is restored from the back/forward cache) to repaint
cart UI without a reload. Without this, adding to cart in one tab left an
already-open tab on a different page showing a stale count/stepper state.

**Multi-size products** (currently just Kefir, 500ml/1L) use `data-variant-root` on the
`.product-info__size-block` wrapper instead of a plain `data-product-id` — each size
button carries its own `data-product-id="kefir-500ml"` / `data-price` / `data-unit-label`,
and clicking one rewrites the wrapper's `data-product-id` in place so the shared
Add/stepper logic (`bump()` in `main.js`) picks it up. That only works because `bump()`
reads `card.dataset.productId` fresh on every click rather than capturing it in a closure
— don't reintroduce that capture, it would silently break variant switching. Each size is
tracked as a fully independent cart line (adding 2× 500ml doesn't affect 1L's quantity).
When a homepage card represents one specific variant (e.g. Kefir's card is the 500ml
default), its `data-product-id` must match that variant's id exactly, or cart state won't
carry over between the card and the detail page.

**CSS gotcha hit while building this:** a relative `url(...)` stored in a CSS custom
property resolves against the *stylesheet's* location when read via `var()`, not the
HTML page's — so `style="--photo: url('assets/images/x.jpg')"` on an element, consumed
via `background: var(--photo)` in `assets/css/styles.css`, resolves to
`assets/css/assets/images/x.jpg` (wrong) instead of `assets/images/x.jpg`. Fix: set the
full `background`/`background-image` inline on the element directly for any per-instance
image (see `kefir.html`'s `.product-hero__image--photo`), and keep the CSS class to only
the size/position/repeat rules that don't contain a URL.

## Closing the loop with Claude Design

Once more than a couple of reusable components exist in code, the `/design-sync` skill
can push this repo's real components up to claude.ai/design, so future design iterations
there are built from Poषण's actual components instead of generic ones. Not applicable yet
