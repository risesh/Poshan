# Poषण — website

Poषण ("foods that heal") is an ecommerce brand for healthy foods rooted in Ayurvedic
tradition. This repo is its website.

## Design system — always use it, never improvise

The brand's colors, type scale, spacing, and component patterns are documented in
[`Design.md`](Design.md) at repo root. That document is the source of truth for what the
brand looks like.

The enforcement mechanism is [`assets/css/tokens.css`](assets/css/tokens.css) — a CSS
custom-property file mirroring `Design.md`'s `:root` block exactly.

**Rules for any new page or component:**
- Import `assets/css/styles.css` (which itself imports `tokens.css`) — don't write a new
  standalone stylesheet.
- Never hardcode a brand hex, font-family, or radius. Use the `var(--*)` tokens
  (`--color-ink`, `--color-teal`, `--color-bone`, `--font-display`, `--font-editorial`,
  `--font-mono`, `--radius-card`, etc.) — see `tokens.css` for the full list.
- Before building a new UI pattern, check whether `styles.css` already has one (nav, hero
  split, product card, pill/attribute tag, philosophy banner). Reuse the existing class
  before inventing a new one.
- If `Design.md` changes (new color, new type rule), update `tokens.css` to match in the
  same change — they must never drift apart.

## Design reference — the exact source, not a vibe

`design/Poshan Homepage (standalone).html` is the raw export from Claude Design
(claude.ai/design), handed over specifically so this site matches it exactly. Treat every
pixel/color/copy value in it as intentional, not negotiable.

**It is not readable as-is.** It's a self-executing JS bundle (a `.dc.html` "standalone"
export) — the real markup lives inside a `<script type="__bundler/template">` tag as a
JSON-escaped string. Use the decoded, greppable copy instead:

- `design/decoded-source.html` — plain HTML/inline-styles, regenerated by
  `python3 design/decode.py` whenever the standalone export is replaced with a newer one.
  Committed, so it's always available without re-running the decoder.
- It's a full-funnel design canvas — homepage (`t1`/`1a`), login/signup (`t2`), product
  detail/cart/our story (`t3`), checkout (`t4`), order confirmation (`t5`). Built so far:
  homepage (`1a` → `index.html`), Our story (`3c` → `our-story.html`), product detail
  (`3a` → `kefir.html` — only product the source fully specifies; the other three product
  pages reuse its template with placeholder ingredient/nutrition content, see below), cart
  (`3b` → `cart.html`, see "Cart page" below), auth (`3d`'s split layout + `2a`-`2e`'s
  field-level detail merged → `signin.html`, see "Auth" below). `orders.html` has no
  source counterpart at all (see "Auth" below). Checkout and order confirmation are
  still reference-only.

**Placeholder content — product pages other than Kefir.** `punjabi-mango-pickle.html`,
`lacto-fermented-carrots.html`, and `dryfruit-millet-laddoo.html` reuse Kefir's template,
but their description/ingredients/nutrition-facts are authored for the prototype (in
Poshan's `Design.md` voice), not sourced — each has an HTML comment saying so. Don't
treat their kcal/ingredient values as real; replace before launch.

**Hard rule for any layout/visual value** (padding, margin, width, font-size, color,
copy text): grep it out of `design/decoded-source.html` first. Never estimate a
percentage from a fixed-pixel value, eyeball a screenshot, or rely on memory of a value
read earlier in the session — the hero's `padding-left` was guessed at `8%`, then
re-guessed at `56px`, before the actual source value (`200px`) was checked. If a value
isn't in the source, say so instead of inventing one.

**Verify, don't eyeball, after building:** spot-check computed layout against literal
source values (e.g. `el.getBoundingClientRect()` in a headless browser vs. the grepped
px numbers) rather than declaring a section done from a screenshot alone.

## Generated data files — same pattern as decode.py

`Quotes.txt` (repo root) is the human-editable source for the rotating footer quote.
`build-quotes.py` parses it into `assets/js/quotes-data.js` (a committed
`window.POSHAN_QUOTES` array — plain `<script>` tag, no fetch/build step, so it works
under `file://` too). Re-run `python3 build-quotes.py` after editing `Quotes.txt`; don't
hand-edit `quotes-data.js`. Any page with the `.philosophy` footer banner should load
`quotes-data.js` before `main.js` and mark its `<blockquote>` with `data-random-quote` —
the quote re-rolls on every load of that page, not just the homepage. Keep the element's
static fallback text as the exact source-authored quote (Leigh Hunt), since that's what
renders if JS is unavailable.

## Cart

`main.js` keeps cart state as `{ productId: qty }` in `localStorage` (key `poshan:cart`),
shared across pages via `[data-cart-link]` nav elements. Product cards opt in with
`data-product-id="<slug>"` on the `.card` element. Clicking `.card__add` swaps it for a
`.card__qty` "− N +" stepper (hidden by default — `.card__qty[hidden]` must explicitly
re-assert `display:none`, since author-origin `display:flex` otherwise beats the UA's
`[hidden]` styling regardless of specificity); decrementing to 0 swaps back to the Add
button. The stepper's visual style is lifted from the product-detail/cart screens in
`design/decoded-source.html` (search `qty` / `−`) — the homepage card was never mocked
up with one. Out-of-stock buttons use the native `disabled` attribute (no
`data-product-id`, no stepper markup), not a JS-level guard.

**`PRODUCT_CATALOG` in `main.js` must be updated whenever a `data-product-id` is added,
removed, or renamed.** It's the source of truth for every addable product (name, badge,
size, price, thumbnail, link) — `getCart()` prunes any stored cart entry whose id isn't a
key in it, and `cart.html` renders its line items from it. (Skipping this after a rename
leaves orphaned cart entries that count toward the nav total but render nowhere —
happened once with `kefir` → `kefir-500ml`.)

**Multi-size products** (currently just Kefir, 500ml/1L) use `data-variant-root` on the
`.product-info__size-block` wrapper instead of a plain `data-product-id` — each size
button carries its own `data-product-id`/`data-price`/`data-unit-label`, and clicking one
rewrites the wrapper's `data-product-id` in place so the shared Add/stepper logic
(`bump()`) picks it up. This depends on `bump()` reading `card.dataset.productId` fresh
on every click rather than closing over it — don't reintroduce that capture. Each size is
a fully independent cart line. A homepage card representing one variant (e.g. Kefir =
500ml) must use that variant's exact id, or cart state won't carry over to the detail page.

**CSS custom-property gotcha:** a relative `url(...)` inside a custom property resolves
against the *stylesheet's* location when read via `var()`, not the page's. Set
`background`/`background-image` inline directly for any per-instance image (see
`kefir.html`) instead of routing a URL through a CSS variable.

## Cart page (cart.html)

Unlike the design source's one static example cart, `cart.html` renders whatever's
actually in `localStorage` against `PRODUCT_CATALOG` — arbitrary product/quantity
combinations, computed subtotal/shipping/total — via `renderCartPage()` in `main.js`,
which rebuilds `#cart-container`'s `innerHTML` from scratch on every cart change.

**Business rules not stated in the source, decided with the user:**
- Shipping: ₹49, free at ₹500+ subtotal.
- No automatic bundle discount — the source's flat `−₹40` line only appears if the promo
  code box is used (any non-empty input + Apply → one-time flat `−₹40`, no real
  validation, nothing persisted).
- Checkout button is an inert placeholder (no checkout page yet).

**Empty-cart state is authored, not sourced** — the design mockup only shows a populated
cart.

**Any future dynamically-rendered block that reuses `data-product-id`** (a wishlist, a
"recently viewed" widget, etc.) **needs the same `:not([data-cart-line])`-style exclusion**
from the generic wiring loop and `renderAllCardQtys` that `cart.html`'s line items use
(see the comment at `renderAllCardQtys` in `main.js`) — otherwise its qty buttons double-fire.

## Auth (signin.html)

Mocked — no real backend, no real OAuth. State is `{ name, email }` in `localStorage`
(key `poshan:auth`), same pattern as cart. Triggered from any page's "Sign in" nav
link, or from `cart.html`'s Checkout button when not yet authenticated (both route to
`signin.html?return=<page>`; completing auth sends the user back there). Merges two
source screens: `3d`'s static-left/dynamic-right split layout with `2a`-`2e`'s
field-level content (sign in, sign in error, sign up, sign up error, post-signup
"a little about you") — the source never mocked up the field-level detail inside the
`3d` layout itself.

**Decisions not stated in the source:**
- Google is the only social sign-in option — Apple was in the source (`2a`-`2e`) but was
  deliberately removed: "Sign in with Apple" requires a paid Apple Developer Program
  membership, Google's OAuth doesn't.
- Sign-in validates shape only (email looks like an email, password non-empty) — there
  are no real accounts to check credentials against, so it can't do more than that. Any
  input passing that bar succeeds.
- "Continue/Sign up with Google" succeeds instantly, no real OAuth. Which tab is
  active decides sign-in-style (straight through) vs. sign-up-style (through the
  about-you step) behavior.
- Sign-up's three validated fields (email shape, password strength, terms checked) are
  exactly the three the source's error state (`2d`) shows and are real, client-checkable
  rules — not mocked. Full name is required but has no styled error, matching the source.
- Once authenticated, the nav's pill-button relabels from "Sign in" to "Sign out"
  (same element, same click-to-sign-out behavior, just text) and a separate
  `[data-orders-link]` "Past orders" link appears next to it — `renderAuthNav()` in
  `main.js` toggles both together. `orders.html` is an authored placeholder (no design
  source for an order-history page — the source only has a single order-confirmation
  receipt, `5a`, and checkout is still reference-only): just an empty state reusing
  `.cart-empty` verbatim, no real order data since there's nothing to generate it from
  yet. Gated with `data-requires-auth` on `<body>` (see below) so it's not reachable
  signed out.

**`data-requires-auth` on `<body>`** makes `main.js` redirect to
`signin.html?return=<page>` immediately if not authenticated — generic, not
orders.html-specific, so any future account-only page can opt in the same way. Client-side
only (no SSR), so there's a brief flash of the page before the redirect fires — same
limitation the Checkout gate already had.

**`KNOWN_PAGES` in `main.js` must be updated whenever a page is added, renamed, or
removed.** It's the whitelist both `return=` redirect targets and the current-page
detector are checked against — an unlisted page silently falls back to `index.html`
rather than erroring, so a forgotten entry doesn't crash, it just quietly sends users
somewhere they didn't ask for.
